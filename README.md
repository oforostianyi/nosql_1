# nosql_1: музична аналітика на MongoDB

Це навчальний проєкт. Я взяв готову таблицю з приблизно 114 тисячами пісень Spotify і завантажив її в хмарну базу даних MongoDB Atlas. У кожної пісні є оцінка популярності від 0 до 100 і кілька характеристик звучання: темп, гучність, наскільки під неї зручно танцювати тощо.

Далі я ставив базі запитання. Які пісні підійдуть для вечірки? У яких виконавців немає жодної слабкої пісні? Які пісні звучать незвично швидко для свого жанру? Яка музика годиться як тихий фон для роботи?

Окрема частина роботи стосується швидкості. База може шукати відповідь двома способами: перебирати всі записи підряд або дивитися в індекс. Індекс схожий на предметний покажчик у кінці книжки. Я заміряв обидва способи і порівняв цифри.

Усі кроки можна повторити. Повний текст того, що виводили скрипти, лежить у папці `results/`: там видно і сам запит, і відповідь бази. Цей текст я використовую замість скріншотів.

## Як запустити з нуля

Потрібні Python 3, програма `mongosh` (це консоль для роботи з MongoDB) і доступ до кластера в Atlas.

```bash
# 1. Встановити бібліотеки Python
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. Створити файл .env з адресою бази. У ньому один рядок:
# MONGO_URI=mongodb+srv://user:password@cluster.mongodb.net/
# У файлі є пароль, тому в git він не потрапляє (див. .gitignore).

# Перед запуском mongosh треба передати адресу з .env у термінал:
export $(grep -m1 '^MONGO_URI=' .env)
echo ${#MONGO_URI}   # має вивести число, більше за нуль
# Якщо пропустити цей крок, mongosh не знатиме адреси і спробує
# підключитися до бази на вашому комп'ютері. Її там немає,
# тому з'явиться помилка ECONNREFUSED.

# 3. Покласти файл dataset.csv у корінь проєкту.
#    Оригінал: https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset
#    Я брав таку саму копію з HuggingFace (maharshipandya/spotify-tracks-dataset).

# 4. Завантажити і перетворити дані (частина 1)
python scripts/01_load_data.py
mongosh "$MONGO_URI" --file scripts/02_transform.js

# 5. Запити (частина 2)
mongosh "$MONGO_URI" --file queries/part2_queries.js

# 6. Звіти та індекси (частина 3)
mongosh "$MONGO_URI" --file queries/part3_analytics.js
mongosh "$MONGO_URI" --file queries/part3_indexes.js
```

Кластер безкоштовний (тариф Atlas M0), називається GoItNoSQLTask01. Atlas одразу тримає дані на трьох серверах, які копіюють один одного (це називається Replica Set). Якщо один сервер вийде з ладу, дані не загубляться. Окремо налаштовувати нічого не треба.

Скрипти можна запускати скільки завгодно разів. Кожен спочатку видаляє те, що створив минулого разу, і робить усе заново.

## Частина 1. Завантаження і будова даних

Спочатку дані потрапляють у базу без жодних змін, у колекцію `tracks_raw`. Колекція в MongoDB приблизно відповідає таблиці у звичайній базі даних. З 114 000 рядків завантажилось 113 999. В одному рядку не було ні назви пісні, ні виконавця, тому я його пропустив. Перед завантаженням скрипт привів значення до правильних типів: числа стали числами, а позначка про нецензурні слова стала значенням «так» або «ні».

Потім база сама переклала записи в нову колекцію `tracks`. Ось що змінилося:

- Виконавці раніше були записані одним рядком через крапку з комою, наприклад «Drake; Future». Тепер це список окремих імен.
- Дванадцять характеристик звучання зібрані в один блок `audio_features`.
- З'явилися два нові поля. `duration_sec` показує тривалість у секундах. `popularity_tier` ділить пісні на три групи за популярністю: high (70 і вище), medium (від 40 до 69) і low (нижче 40).

Так виглядає один запис:

```javascript
{
  track_id: '5SuOikwiRyPMVoIQDJUgSV',  // код пісні в каталозі Spotify
  track_name: 'Comedy',
  album_name: 'Comedy',
  artists: ['Gen Hoshino'],            // список імен, а не рядок
  popularity: 73,                      // оцінка від 0 до 100
  popularity_tier: 'high',
  duration_ms: 230666,
  duration_sec: 230.7,
  explicit: false,                     // чи є нецензурні слова
  track_genre: 'acoustic',
  audio_features: {
    danceability: 0.676,   // наскільки під пісню зручно танцювати, від 0 до 1
    energy: 0.461,         // наскільки пісня енергійна
    loudness: -6.746,      // гучність у децибелах (ближче до нуля означає гучніше)
    speechiness: 0.143,    // скільки в пісні мовлення замість музики
    acousticness: 0.0322,  // наскільки звучання акустичне, «живе»
    instrumentalness: 0.00000101, // наскільки пісня без вокалу
    liveness: 0.358,       // наскільки схоже на запис живого концерту
    valence: 0.715,        // настрій: 0 сумний, 1 веселий
    tempo: 87.917,         // темп, удари за хвилину (BPM)
    key: 1, mode: 0, time_signature: 4  // тональність і розмір такту
  }
}
```

### Питання 1. Навіщо характеристики зібрані в окремий блок audio_features?

Можна уявити письмовий стіл. На ньому можна розкласти дванадцять окремих карток з характеристиками пісні, а можна покласти їх в одну папку з підписом «звучання». Блок `audio_features` і є такою папкою.

Чому так зручніше:

- Усі ці характеристики описують одне: як звучить пісня. Spotify теж видає їх одним набором. Їх зазвичай читають разом. Тому на верхньому рівні запису лишаються тільки основні дані пісні: назва, виконавці, популярність, жанр.
- Весь блок можна замінити, скопіювати або видалити однією командою, не перелічуючи всі дванадцять полів.
- Якщо потрібні всі характеристики одразу, у запиті досить написати `audio_features: 1`.

Коли такий блок заважає:

- Назви полів у запитах стають довшими: треба писати не `energy`, а `audio_features.energy`. Якщо майже всі запити працюють з окремими характеристиками, з плоским списком полів працювати простіше.
- Якщо значення всередині блоку часто змінюються, при кожній дрібній зміні база переписує весь запис. Такі дані краще тримати окремо.
- Коли блоки вкладені один в один у три й більше рівні, запити важко читати. У нас лише один рівень, тож тут цієї проблеми немає.

Для цих даних окремий блок підходить добре: характеристики записали один раз, і далі їх тільки читають.

### Питання 2. Чому виконавці записані списком, а не рядком?

Рядок «Daddy Yankee;Bad Bunny» для бази просто шматок тексту. Щоб знайти в ньому Bad Bunny, базі доведеться шукати ці слова всередині тексту кожного з майже 114 тисяч записів. Це повільно. До того ж можна отримати хибний збіг, якщо ім'я одного виконавця є частиною імені іншого. Лишній пробіл теж може зіпсувати пошук. А щоб порахувати, скільки виконавців у пісні, довелося б рахувати крапки з комою.

Список база розуміє інакше: кожне ім'я в ньому окреме значення. За такими значеннями можна зробити індекс і шукати точно.

| Що шукаємо | Коли виконавці записані списком | Коли виконавці записані рядком |
|---|---|---|
| Усі пісні одного виконавця | `{artists: "Bad Bunny"}` | пошук слів у тексті, повільно і з помилками |
| Пісні, де разом є два певні виконавці | `{artists: {$all: ["Daddy Yankee","Bad Bunny"]}}` | два пошуки по тексту, результат залежить від порядку імен |
| Пісні будь-кого з кількох виконавців | `{artists: {$in: [...]}}` | довгий запит з кількох пошуків по тексту |
| Сольні пісні | `{artists: {$size: 1}}` | рахувати крапки з комою в тексті |
| Звіти по виконавцях | один крок `$unwind` | щоразу розрізати рядок на імена |

Різницю я заміряв (див. розділ про індекси нижче). Коли виконавці записані списком і є індекс, пошук пісень Bad Bunny читає 416 записів замість 113 999 і працює приблизно в 40 разів швидше.

## Частина 2. Запити (`queries/part2_queries.js`)

У файлі `results/part2_output.txt` перед кожною відповіддю надруковано сам запит, тож видно, про що саме питали базу.

### Завдання 1. Пісні для вечірки

Шукаємо пісні, під які добре танцювати. Танцювальність і енергійність мають бути більші за 0.7, а тривалість від 3 до 5 хвилин.

```javascript
db.tracks.find({
  "audio_features.danceability": { $gt: 0.7 },
  "audio_features.energy": { $gt: 0.7 },
  duration_ms: { $gte: 180000, $lte: 300000 }
}).sort({ popularity: -1 })
```

Знайшлося 7 311 записів. Але різних пісень серед них менше, 5 328. Річ у тім, що одна пісня може бути в базі кілька разів, окремо для кожного свого жанру (докладніше в розділі «Про повтори в даних» нижче). Найпопулярніші пісні: «Quevedo: Bzrp Music Sessions, Vol. 52» (оцінка 99) і «Me Porto Bonito» (97).

### Завдання 2. Виконавці, у яких усі пісні популярні

Умова така: у виконавця щонайменше 3 пісні, і навіть найменш популярна з них має оцінку 60 або вище. Тобто дивимося не на середню оцінку, а на найнижчу. Якщо хоч одна пісня слабка, виконавець не проходить.

Запит складається з кількох кроків, які база виконує по черзі:

1. `$unwind` робить з однієї пісні кілька рядків, по одному на кожного виконавця. Так спільна пісня зараховується кожному з них.
2. Прибираємо повтори. Групуємо рядки за парою «виконавець і код пісні», тож кожна пісня рахується один раз, навіть якщо вона є в базі в чотирьох жанрах. Іноді копії однієї пісні мають трохи різну оцінку (дані могли знімати в різні дні). Тоді беремо більшу.
3. Для кожного виконавця рахуємо кількість пісень, найнижчу і середню оцінку.
4. Лишаємо тих, у кого щонайменше 3 пісні і найнижча оцінка не менша за 60.
5. Округлюємо середню оцінку до одного знака після коми, сортуємо від більшої до меншої і беремо перших 20.

Без другого кроку результат був би неправильним, бо запит рахував би записи, а не пісні. Наприклад, Luar La L тоді опинявся на другому місці з чотирма піснями. Насправді в нього одна пісня, «Caile», яка просто є в базі чотири рази: у жанрах latin, latino, reggae і reggaeton. У Måneskin так само було 12 записів, але лише 5 різних пісень.

Перші п'ять місць:

| Виконавець | Пісень | Найнижча оцінка | Середня оцінка |
|---|---|---|---|
| Harry Styles | 3 | 89 | 92.0 |
| Olivia Rodrigo | 5 | 86 | 87.4 |
| IVE | 3 | 79 | 84.0 |
| Morgan Wallen | 3 | 81 | 83.3 |
| One Direction | 5 | 80 | 83.0 |

Одна примітка щодо Harry Styles. Я вважаю однією піснею один код `track_id`. Але Spotify може дати одній і тій самій пісні два різні коди, якщо вона вийшла і окремим синглом, і в альбомі. Тому «As It Was» порахована двічі (коди різні, оцінки 95 і 92), а разом з «Watermelon Sugar» виходить три пісні. Якби рахувати за назвами, пісень було б дві, і Harry Styles не пройшов би умову. Рахувати за назвами я не став, бо різні пісні часто мають однакові назви, і тоді вони б злилися в одну.

### Завдання 3. Незвично швидкі пісні в кожному жанрі

Для кожного жанру база рахує середній темп і те, наскільки темп пісень зазвичай відрізняється від середнього. Цю типову різницю називають стандартним відхиленням, для неї є функція `$stdDevPop`. Межу задаємо так: середній темп плюс два стандартні відхилення. Пісня, швидша за цю межу, вважається незвично швидкою для свого жанру. Наприклад, у жанрі acoustic середній темп 119 ударів за хвилину, а межа виходить 178.5.

Кроки запиту:

1. `$group` збирає для кожного жанру середній темп, відхилення і список усіх пісень.
2. Рахуємо межу для жанру.
3. `$filter` лишає в списку тільки пісні, швидші за межу.
4. Жанри, де таких пісень немає, відкидаємо.

Вийшло 112 жанрів, у яких є незвично швидкі пісні, разом 3 506 пісень. Це приблизно 3% усіх записів. Для такого способу пошуку це очікувана частка, тож результат схожий на правду. У жанрі acoustic таких пісень 34. Найшвидші з них: «Fast Car» у виконанні Boyce Avenue та Kina Grannis (205 ударів за хвилину), акустична версія «Running Up That Hill» від Jonah Baker (203.8) і «Wanted Man» від Mat Kearney (203.7). Можливо, частина цих пісень не така вже й швидка, а Spotify просто порахував удари вдвічі частіше, ніж їх чує людина.

У консоль скрипт виводить тільки три приклади. Повний список зберігається в колекцію `spotify.tempo_outliers`, по одному запису на жанр, тобто 112 записів. Подивитися його можна командою `db.tempo_outliers.find().sort({genre: 1})`. Для збереження використано `$out`: він щоразу повністю переписує колекцію, тому після повторного запуску записи не дублюються.

### Завдання 4. Музика для фону під час роботи

Умови: пісня тиха (гучність нижче -10 децибел), у ній майже немає слів (мовлення менше 0.1), вона переважно інструментальна (більше 0.5) і без нецензурних слів.

```javascript
db.tracks.find({
  "audio_features.loudness": { $lt: -10 },
  "audio_features.speechiness": { $lt: 0.1 },
  "audio_features.instrumentalness": { $gt: 0.5 },
  explicit: false
}).sort({ popularity: -1 })
```

Знайшлося 9 324 записи. Для пошуку такої музики в частині 3 зроблено окремий індекс.

## Додаткові звіти (`queries/part3_analytics.js`)

Це вже понад обов'язкові завдання. Тут звіти, де дані з двох колекцій з'єднуються (`$lookup`) і де списки виконавців розкладаються на окремі рядки (`$unwind`). Повний вивід лежить у `results/part3_analytics_output.txt`.

Що вийшло:

- Найвища середня оцінка в жанрів pop-film (59.3), k-pop (57.0) і chill (53.7). У жанрі pop найбільша частка хітів: 31.7% пісень мають оцінку 70 і вище. Водночас середня оцінка в pop лише 47.6. Тобто в pop багато дуже популярних пісень і багато таких, які майже ніхто не слухає.
- Популярних пісень мало. Оцінку 70 і вище мають лише 4.8% пісень (5 472). Від 40 до 69 мають 37.8% (43 115). Решта, 57.4% (65 412), мають оцінку нижче 40.
- Звіт по виконавцях зберігається в колекцію `artist_stats`. Туди потрапили 3 527 виконавців, у яких щонайменше 10 записів. Потім цей звіт приєднується до найпопулярніших пісень через `$lookup`. Наприклад, пісня «Unholy» має оцінку 100, а середня оцінка всіх 16 записів Kim Petras лише 19.1. Один великий хіт ще не робить виконавця стабільно популярним.
- Я перевірив, чи енергійні пісні популярніші за спокійні. Усі пісні поділено на п'ять груп за енергійністю. Середня оцінка в групах майже однакова, від 28.9 до 35.4. Отже, енергійність сама по собі на популярність майже не впливає.

## Частина 3. Індекси: як база шукає швидше (`queries/part3_indexes.js`)

Спочатку коротко про те, що тут відбувається.

Індекс схожий на предметний покажчик у кінці книжки. Без покажчика, щоб знайти потрібне слово, доводиться гортати всі сторінки. З покажчиком одразу видно, на яких сторінках воно є. Так само база без індексу читає всі 113 999 записів підряд (у звіті бази цей спосіб називається COLLSCAN). З індексом вона спочатку дивиться в покажчик (IXSCAN) і потім читає лише ті записи, які підходять.

Команда `explain()` просить базу виконати запит і показати, як саме вона його виконувала: чи користувалася індексом, скільки записів прочитала і скільки часу на це пішло. Я запускав її для того самого запиту двічі: до створення індексу і після. Усі цифри нижче взяті з файлу `results/part3_indexes_output.txt`.

### Завдання 1. Запит із сортуванням

Запит з умови завдання: пісні жанру pop з танцювальністю 0.7 і вище, відсортовані від найпопулярніших.

```javascript
db.tracks.find({
  track_genre: "pop",
  "audio_features.danceability": { $gte: 0.7 }
}).sort({ popularity: -1 }).toArray();
```

Індекс із трьох полів, саме в такому порядку:

```javascript
db.tracks.createIndex(
  { track_genre: 1, popularity: -1, "audio_features.danceability": 1 },
  { name: "idx_genre_pop_dance" }
)
```

Порядок полів важливий. Першим іде жанр, бо його шукаємо за точним значенням. Другою йде популярність, бо за нею сортуємо. Останньою йде танцювальність, бо для неї задано діапазон «від 0.7 і вище». Тоді база одразу переходить до частини покажчика з жанром pop, пісні там уже стоять у порядку популярності, а танцювальність вона перевіряє по ходу. Таке правило порядку полів має назву ESR: Equality (точне значення), Sort (сортування), Range (діапазон).

Результати замірів:

| Що показує explain | Без індексу | З індексом |
|---|---|---|
| Як шукали (stages) | SORT + COLLSCAN | FETCH + IXSCAN |
| Час, мілісекунди | 71 | 2 |
| Скільки записів прочитано (totalDocsExamined) | 113 999 | 354 |
| Скільки рядків покажчика переглянуто (totalKeysExamined) | 0 | 412 |
| Скільки записів повернуто (nReturned) | 354 | 354 |

Без індексу база прочитала всі 113 999 записів, вибрала з них потрібні, а потім окремо відсортувала їх (стадія SORT). З індексом вона одразу знайшла в покажчику жанр pop і прочитала 354 записи, які вже стояли в потрібному порядку. Окреме сортування стало непотрібним, тому стадії SORT у плані більше немає. Запит став приблизно в 35 разів швидшим, а прочитаних записів стало приблизно в 320 разів менше.

Рядків покажчика база переглянула 412, а записів повернула 354. Різниця в 58 записів означає пісні жанру pop з танцювальністю нижче 0.7. База відкинула їх ще під час перегляду покажчика і самі записи не читала.

Як переконатися, що база справді скористалася індексом. У звіті `explain()` замість COLLSCAN стоїть IXSCAN. Поруч указано назву індексу (`indexName: "idx_genre_pop_dance"`) і його поля (`keyPattern`). Кількість переглянутих рядків покажчика більша за нуль. Стадії SORT немає. Усі ці значення є у файлі з виводом.

### Завдання 2. Індекс для музики під час роботи

За умовою завдання таку музику часто шукають за трьома полями: `explicit`, `audio_features.instrumentalness` і `audio_features.speechiness`. Для них зроблено окремий індекс:

```javascript
db.tracks.createIndex(
  { explicit: 1, "audio_features.instrumentalness": 1, "audio_features.speechiness": 1 },
  { name: "idx_work_music" }
)
```

Поле `explicit` стоїть першим, бо його шукаємо за точним значенням (false). Друге поле, інструментальність, відсіює найбільше непотрібних пісень. Мовлення перевіряється останнім.

Для заміру я взяв запит саме за цими трьома полями, без умови про гучність. Тому записів тут більше, ніж у завданні 4 частини 2: 16 141 замість 9 324.

| Що показує explain | Без індексу | З індексом |
|---|---|---|
| Як шукали | COLLSCAN | FETCH + IXSCAN |
| Час, мілісекунди | 125 | 37 |
| Скільки записів прочитано | 113 999 | 16 141 |
| Скільки рядків покажчика переглянуто | 0 | 16 602 |
| Скільки записів повернуто | 16 141 | 16 141 |

Прочитаних записів стало в 7 разів менше, а запит став у 3.4 раза швидшим. Це менший виграш, ніж у завданні 1, і так і має бути. Під цю умову підходить приблизно кожна сьома пісня в базі. Індекс найбільше допомагає тоді, коли треба знайти кілька записів серед багатьох, а не велику частину всіх даних.

### Завдання 3 (необов'язкове). Чи є запит покривним?

Питання з умови. Індекс `{track_genre, popularity, danceability}` із завдання 1 уже створений. Чи є покривним такий запит:

```javascript
db.tracks.find({ track_genre: "pop", popularity: { $gte: 70 } });
```

Покривний запит (covered query) означає, що база може дати відповідь, дивлячись тільки в індекс, і зовсім не відкриваючи самі записи. Для цього все, що запит повертає, має бути в індексі.

Відповідь: у такому вигляді запит не покривний. На це дві причини:

1. Запит не вказує, які поля йому потрібні, тому база повертає весь запис: назву, виконавців, характеристики звучання тощо. Цих полів в індексі немає, тож базі доводиться читати самі записи.
2. Навіть якщо попросити тільки поля з індексу, база за замовчуванням додає ще службове поле `_id`. Його в цьому індексі теж немає. Тому треба окремо написати `_id: 0`, тобто «не повертай це поле».

Я перевірив обидва варіанти через `explain()`:

| Варіант запиту | Стадії | Скільки записів прочитано | Скільки рядків покажчика переглянуто |
|---|---|---|---|
| Як в умові, без переліку полів | FETCH + IXSCAN | 317 | 317 |
| З переліком полів `{_id: 0, track_genre: 1, popularity: 1}` | PROJECTION_COVERED + IXSCAN | 0 | 317 |

Другий варіант уже покривний. База не прочитала жодного запису (totalDocsExamined = 0) і зібрала відповідь з 317 рядків покажчика. Це видно і з назви стадії PROJECTION_COVERED у звіті.

### Додатково. Індекс за списком виконавців

Індекс за полем, де лежить список, називається multikey. База записує в покажчик кожне ім'я зі списку окремо. Для запиту `{artists: "Bad Bunny"}` час зменшився з 81 до 2 мілісекунд, а кількість прочитаних записів зі 113 999 до 416. Саме на цей замір я посилаюся у відповіді на питання 2 частини 1.

### Усі індекси колекції tracks

| Назва | Поля | Для чого |
|---|---|---|
| idx_genre_pop_dance | жанр, популярність (від більшої до меншої), танцювальність | завдання 1 і покривний запит у завданні 3 |
| idx_work_music | explicit, інструментальність, мовлення | пошук музики для роботи |
| idx_artists_multikey | виконавці (список) | пошук за іменем виконавця |

## Про повтори в даних

У базі 113 999 записів, але різних пісень серед них лише 89 740. Так сталося, бо автори датасету збирали пісні по жанрах, приблизно по тисячі на кожен жанр. Якщо пісня належить до кількох жанрів, вона потрапила в кожну з цих добірок. Наприклад, «Ferrari» (James Hype) є в базі чотири рази: у жанрах dance, deep-house, groove і house. Усього таких повторних записів 24 259.

Це особливість самих даних, а не помилка під час завантаження. Звітам по жанрах це не заважає, бо в межах одного жанру пісня трапляється один раз. Там, де рахуються пісні виконавця (завдання 2 частини 2), повтори прибрано окремим кроком. У завданні 1 наведено обидва числа: скільки записів і скільки різних пісень. У додаткових звітах по всій базі пісні з кількох жанрів мають трохи більшу вагу, ніж інші. Це варто мати на увазі, коли читаєте ті цифри.

Якщо колись знадобиться колекція без повторів, записи можна згрупувати за кодом пісні і зібрати всі її жанри в один список.
