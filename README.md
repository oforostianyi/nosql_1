# nosql_1 — музична аналітика на MongoDB

Це навчальний проєкт. Ми взяли готову таблицю з приблизно 114 тисячами пісень Spotify (кожна пісня має оцінку популярності й набір «технічних характеристик»: темп, гучність, танцювальність тощо), завантажили її в хмарну базу MongoDB Atlas і навчилися ставити їй запитання: які пісні підійдуть для вечірки, у яких виконавців немає провальних треків, де в жанрах трапляються підозріло швидкі пісні.

Окрема частина роботи — про швидкість. База може шукати відповідь двома способами: переглядати всі записи поспіль або користуватися «змістом книжки» — індексом. Ми навмисно заміряли обидва способи й показали різницю в цифрах.

Усі команди можна повторити самостійно. Повні логи роботи скриптів лежать у папці `results/` — там видно і сам запит, і відповідь бази. Це замінює скріншоти: текст надійніший, його можна перечитати й перевірити.

## Як запустити з нуля

Потрібні Python 3, програма `mongosh` (консоль MongoDB) і доступ до кластера Atlas.

```bash
# 1. Бібліотеки Python
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. Файл .env з адресою бази. Один рядок:
# MONGO_URI=mongodb+srv://user:password@cluster.mongodb.net/
# Файл із паролем не комітимо — він у .gitignore.

# Перш ніж запускати mongosh, передайте адресу з .env у термінал:
export $(grep -m1 '^MONGO_URI=' .env)
echo ${#MONGO_URI}   # має бути більше нуля
# Без цього кроку mongosh не знає адреси й стукає на локальний комп'ютер,
# де бази немає — звідси помилка ECONNREFUSED.

# 3. Файл dataset.csv покласти в корінь проєкту.
#    Оригінал: https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset
#    Ми брали його публічну копію з HuggingFace (maharshipandya/spotify-tracks-dataset).

# 4. Завантаження і переформатування даних (частина 1)
python scripts/01_load_data.py
mongosh "$MONGO_URI" --file scripts/02_transform.js

# 5. Запити (частина 2)
mongosh "$MONGO_URI" --file queries/part2_queries.js

# 6. Аналітика й індекси (частина 3)
mongosh "$MONGO_URI" --file queries/part3_analytics.js
mongosh "$MONGO_URI" --file queries/part3_indexes.js
```

Кластер — безкоштовний Atlas M0 з назвою GoItNoSQLTask01. Він уже налаштований як Replica Set із трьох серверів (копія даних лежить на кожному, тож вихід одного сервера з ладу нічого не втрачає). Нічого додатково налаштовувати не треба.

Скрипти можна запускати повторно: кожен сам прибирає свої попередні результати й створює їх заново.

## Частина 1. Завантаження і схема даних

Спершу дані лягають у базу «як є» — колекція `tracks_raw` (колекція в MongoDB — це приблизно те саме, що таблиця). Зі 114 000 рядків таблиці завантажилось 113 999: в одному рядку не було ні назви пісні, ні виконавця, такий запис ми відкинули. Перед завантаженням текст із таблиці перетворили на нормальні типи: числа стали числами, позначка «нецензурний контент» — так/ні.

Потім сама база переформатувала записи в колекцію `tracks`. Що змінилося:

- виконавці були одним рядком через крапку з комою («Drake; Future») — стали списком імен;
- дванадцять характеристик звучання зібрали в один блок `audio_features`;
- додали два поля, яких у таблиці не було: тривалість у секундах (`duration_sec`) і категорію популярності (`popularity_tier`: high від 70, medium від 40, low нижче 40).

Ось як виглядає один запис:

```javascript
{
  track_id: '5SuOikwiRyPMVoIQDJUgSV',  // код пісні в каталозі Spotify
  track_name: 'Comedy',
  album_name: 'Comedy',
  artists: ['Gen Hoshino'],            // список, а не рядок
  popularity: 73,                      // оцінка від 0 до 100
  popularity_tier: 'high',
  duration_ms: 230666,
  duration_sec: 230.7,
  explicit: false,                     // чи є нецензурний контент
  track_genre: 'acoustic',
  audio_features: {
    danceability: 0.676,   // наскільки підходить для танців, від 0 до 1
    energy: 0.461,         // енергійність
    loudness: -6.746,      // гучність у децибелах (що ближче до 0, то гучніше)
    speechiness: 0.143,    // скільки в треку мовлення, а не музики
    acousticness: 0.0322,  // «живе» акустичне звучання
    instrumentalness: 0.00000101, // чи це музика без вокалу
    liveness: 0.358,       // схожість на живий виступ
    valence: 0.715,        // настрій: 0 — сумно, 1 — весело
    tempo: 87.917,         // швидкість в ударах за хвилину (BPM)
    key: 1, mode: 0, time_signature: 4  // тональність і розмір такту
  }
}
```

### Питання 1. Навіщо характеристики сховали в блок audio_features?

Уявіть робочий стіл. Можна розкидати по ньому дванадцять карток із характеристиками пісні, а можна скласти їх в одну папку з написом «звучання». Папка — це і є `audio_features`.

Чому папка зручніша:

- Характеристики — це одна тема. Вони прийшли з одного джерела (сервіс Spotify так само віддає їх одним пакетом), разом читаються і ніколи не змінюються окремо одна від одної. Поряд на верхньому рівні лишається тільки «паспорт» пісні: назва, виконавці, популярність.
- Весь блок можна замінити, скопіювати чи видалити однією командою, не перелічуючи дванадцять полів.
- Коли потрібні всі характеристики, досить попросити `audio_features: 1` — один рядок замість дванадцяти.

Коли папка заважає:

- Назви полів у запитах стають довшими: не `energy`, а `audio_features.energy`. Якщо запити щодня ганяють по окремих характеристиках, плоский список полів писати простіше.
- Якщо дані всередині блока часто міняються, кожне дрібне оновлення змушує базу переписувати весь запис. Для часто змінюваних даних краще винести їх окремо.
- Глибокі «папки в папках» (три рівні й більше) роблять запити важкими для читання. У нас лише один рівень, тож цієї проблеми немає.

Для цього датасету блок — правильний вибір: характеристики записані раз і далі тільки читаються.

### Питання 2. Чому виконавці — список, а не рядок?

Рядок «Daddy Yankee;Bad Bunny» база бачить як суцільний текст. Щоб знайти в ньому Bad Bunny, доводиться шукати підрядок у тексті кожного зі 114 тисяч записів. Це повільно, і це ламається на дрібницях: ім'я одного виконавця може міститися в імені іншого, пробіл не там — і збіг уже не той. Порахувати, скільки виконавців у пісні, теж неможливо без хитрощів.

Список імен база розуміє по-справжньому: кожне ім'я — окреме значення, за ним можна побудувати індекс і шукати точно.

| Що шукаємо | Зі списком | З рядком |
|---|---|---|
| Усі пісні виконавця | `{artists: "Bad Bunny"}` | пошук підрядка в тексті, повільно і з помилками |
| Пісню, де двоє конкретних виконавців разом | `{artists: {$all: ["Daddy Yankee","Bad Bunny"]}}` | два текстові пошуки, результат залежить від порядку імен |
| Будь-кого зі списку імен | `{artists: {$in: [...]}}` | довга конструкція з кількох текстових пошуків |
| Сольні пісні / з трьома виконавцями | `{artists: {$size: 1}}` | рахувати крапки з комою в тексті |
| Звіти по виконавцях | один крок `$unwind` | щоразу різати рядок на шматки |

Різниця виміряна (розділ про індекси нижче): пошук пісень Bad Bunny зі списком та індексом читає 416 записів замість 113 999 і працює близько 40 разів швидше.

## Частина 2. Запити (`queries/part2_queries.js`)

У логах `results/part2_output.txt` перед кожною відповіддю надрукований сам запит — можна бачити, що саме питали в бази.

### Завдання 1. Пісні для вечірки

Шукаємо те, під що добре танцювати: танцювальність і енергійність вище 0.7, тривалість від 3 до 5 хвилин.

```javascript
db.tracks.find({
  "audio_features.danceability": { $gt: 0.7 },
  "audio_features.energy": { $gt: 0.7 },
  duration_ms: { $gte: 180000, $lte: 300000 }
}).sort({ popularity: -1 })
```

Знайшлося 7 311 записів. Але це не 7 311 різних пісень: у датасеті одна пісня може лежати кілька разів, по разу на кожен свій жанр (докладніше — у розділі «Про дублікати» нижче). Різних пісень тут 5 328. Найпопулярніші з них — «Quevedo: Bzrp Music Sessions, Vol. 52» (оцінка 99) і «Me Porto Bonito» (97).

### Завдання 2. Виконавці, у яких усі пісні популярні

Умова: щонайменше 3 пісні, і найслабша з них має оцінку 60 або вище. Тобто дивимося не на середнє, а на мінімум: одна провальна пісня — і виконавець не проходить.

Пайплайн (ланцюжок кроків обробки) такий:

1. `$unwind` розкладає кожну пісню на стільки рядків, скільки в ній виконавців, — спільна пісня зараховується кожному.
2. Прибираємо дублікати: групуємо за парою «виконавець + код пісні». Один трек рахується один раз, хоч би в чотирьох жанрах він лежав. Якщо копії мають трохи різну популярність (буває, дані знімали в різні дні), беремо найбільшу.
3. Рахуємо по кожному виконавцю: кількість пісень, мінімальну і середню популярність.
4. Лишаємо тих, у кого пісень не менше 3 і мінімум не нижче 60.
5. Округлюємо середнє до одного знака, сортуємо, беремо 20 найкращих.

Крок 2 тут не формальність. Без нього запит рахував записи, а не пісні, і давав неправду: Luar La L потрапляв на друге місце з «чотирма піснями», хоча це одна-єдина пісня «Caile», розкладена по жанрах latin, latino, reggae і reggaeton. У Måneskin було 12 записів, а пісень — 5.

Перші місця після виправлення:

| Виконавець | Пісень | Мінімум | Середнє |
|---|---|---|---|
| Harry Styles | 3 | 89 | 92.0 |
| Olivia Rodrigo | 5 | 86 | 87.4 |
| IVE | 3 | 79 | 84.0 |
| Morgan Wallen | 3 | 81 | 83.3 |
| One Direction | 5 | 80 | 83.0 |

Чесне застереження про Harry Styles. Ми вважаємо «однією піснею» один код `track_id`. Але Spotify дає різні коди одному запису, якщо він вийшов і синглом, і в альбомі. Тому «As It Was» у нього порахована двічі (коди різні, оцінки 95 і 92), плюс «Watermelon Sugar» — разом три. Якби рахувати за назвами, пісень було б дві й він би не пройшов поріг. Рахувати за назвами ми свідомо не стали: різні пісні часто називаються однаково, і таке згортання злипло б їх докупи.

### Завдання 3. Підозріло швидкі пісні в жанрах

Для кожного жанру рахуємо середній темп і те, наскільки сильно пісні зазвичай від нього відхиляються (це відхилення називається стандартним, функція `$stdDevPop`). Якщо пісня швидша за «середнє плюс два відхилення» — для свого жанру вона нетипово швидка. Наприклад, у спокійному acoustic середній темп 119 ударів за хвилину, поріг виходить 178.5 — усе, що швидше, виглядає дивно.

Кроки пайплайну: `$group` по жанру (середнє, відхилення, список пісень) → обчислюємо поріг → `$filter` лишає в списку тільки пісні вище порогу → жанри без таких пісень відкидаємо.

Вийшло 112 жанрів із «викидами», разом 3 506 пісень — близько 3% від усієї бази. Це схоже на те, що дає правило двох відхилень для звичайного розподілу даних, тож результат виглядає правдоподібно. У acoustic таких пісень 34; найшвидші — «Fast Car» у виконанні Boyce Avenue та Kina Grannis (205 ударів за хвилину), акустична версія «Running Up That Hill» Jonah Baker (203.8) і «Wanted Man» Mat Kearney (203.7). Швидкий темп в acoustic-жанрі — це або незвична аранжовка, або особливість того, як сервіс порахував темп.

У консоль виводяться три приклади, а повний список збережений у колекцію `spotify.tempo_outliers` (112 документів, по одному на жанр). Подивитися: `db.tempo_outliers.find().sort({genre: 1})`. Збереження йде через `$out` — він перезаписує колекцію цілком, тож повторний запуск не плодить дублікатів.

### Завдання 4. Музика для роботи у фоні

Критерії: тихо (гучність нижче -10 децибел), майже без слів (мовлення менше 0.1), переважно інструментальна (більше 0.5), без нецензурного контенту.

```javascript
db.tracks.find({
  "audio_features.loudness": { $lt: -10 },
  "audio_features.speechiness": { $lt: 0.1 },
  "audio_features.instrumentalness": { $gt: 0.5 },
  explicit: false
}).sort({ popularity: -1 })
```

Знайшлося 9 324 пісні. Саме під цей запит у частині 3 зроблено окремий індекс.

## Додаткова аналітика (`queries/part3_analytics.js`)

Це понад обов'язкові завдання — пункт 3 «ходу роботи» про звіти з'єднанням даних ($lookup) і розкладанням списків ($unwind). Логи — у `results/part3_analytics_output.txt`.

Коротко, що показали звіти:

- Найпопулярніші в середньому жанри: pop-film (59.3), k-pop (57.0), chill (53.7). При цьому в жанрі pop найбільша частка справжніх хітів (31.7% пісень з оцінкою 70+), хоча середня оцінка лише 47.6. Схоже, pop — жанр «або вистрілив, або ніхто не почув».
- Популярність розподілена нерівно: пісень з оцінкою 70+ лише 4.8% (5 472), від 40 до 69 — 37.8% (43 115), решта 57.4% (65 412) — нижче 40.
- Звіт по виконавцях зберігається в колекцію `artist_stats` (3 527 виконавців, у яких 10+ пісень). Далі він приєднується до хітів через `$lookup` — виходить цікава картина: пісня «Unholy» має оцінку 100, але середня оцінка всіх 16 пісень Kim Petras — 19.1. Один вірусний хіт ще не робить виконавця стабільно популярним.
- Перевірили припущення «енергійні пісні популярніші». Розбили всі пісні на п'ять груп за енергійністю — середня популярність у групах майже однакова (від 28.9 до 35.4). Тобто ні, енергійність сама по собі популярності не додає.

## Частина 3. Індекси: як база шукає швидко (`queries/part3_indexes.js`)

Два слова про те, що тут відбувається, для тих, хто не працював з базами.

Індекс — це як зміст наприкінці книжки: замість гортати всі сторінки, ви дивитеся в покажчик і одразу відкриваєте потрібну. Без індексу база читає всі 113 999 записів поспіль (у звітах це називається COLLSCAN). З індексом — іде по покажчику (IXSCAN) і дістає лише потрібні записи.

Команда `explain()` каже базі: «не виконуй запит, а розкажи, як ти його виконуватимеш і скільки роботи це коштує». Ми викликали її до створення індексу і після, з однаковим запитом. Усі значення нижче — з логів `results/part3_indexes_output.txt`.

### Завдання 1. Запит із сортуванням

Запит з умови: поп-жанр, танцювальність від 0.7, відсортувати за популярністю.

```javascript
db.tracks.find({
  track_genre: "pop",
  "audio_features.danceability": { $gte: 0.7 }
}).sort({ popularity: -1 }).toArray();
```

Створюємо індекс із трьох полів у такому порядку:

```javascript
db.tracks.createIndex(
  { track_genre: 1, popularity: -1, "audio_features.danceability": 1 },
  { name: "idx_genre_pop_dance" }
)
```

Порядок не випадковий. Спершу поле, за яким шукаємо точний збіг (жанр), потім поле сортування (популярність), і лише потім поле з діапазоном (танцювальність). Так покажчик одразу звужується до одного жанру, записи в ньому вже стоять у потрібному порядку, а діапазон перевіряється по дорозі. Це правило називають ESR: Equality (рівність), Sort (сортування), Range (діапазон).

Що показали заміри:

| Поле зі звіту explain | Без індексу | З індексом |
|---|---|---|
| Як шукали (stages) | SORT + COLLSCAN | FETCH + IXSCAN |
| Час, мілісекунд | 71 | 2 |
| Скільки записів прочитали (totalDocsExamined) | 113 999 | 354 |
| Скільки ключів покажчика переглянули (totalKeysExamined) | 0 | 412 |
| Скільки записів повернули (nReturned) | 354 | 354 |

Людською мовою: раніше база перегортала всі 113 999 «сторінок», вибирала підходящі й потім окремо сортувала їх у пам'яті (стадія SORT). Тепер вона відкриває «зміст» на розділі pop і дістає 354 записи, вже відсортовані за популярністю. Сортувати нічого не треба — стадія SORT з плану зникла зовсім. Швидкість виросла приблизно в 35 разів, а читання з диска скоротилося в 320 разів.

Дрібна деталь: ключів переглянули 412, а записів повернули 354. Різниця — 58 поп-пісень з низькою танцювальністю: база відсіяла їх ще в покажчику, не читаючи самі записи.

Як переконатися, що працює саме індекс: у звіті explain замість COLLSCAN стоїть IXSCAN, поруч указані назва індексу (`indexName: "idx_genre_pop_dance"`) і його поля (`keyPattern`), лічильник ключів більший за нуль, а стадії SORT немає. Усі ці значення є в логах.

### Завдання 2. Індекс для робочої музики

Запит із завдання 4 частини 2 ганяють часто, тож під нього робимо свій покажчик:

```javascript
db.tracks.createIndex(
  { explicit: 1, "audio_features.instrumentalness": 1, "audio_features.speechiness": 1 },
  { name: "idx_work_music" }
)
```

Поле `explicit` стоїть першим, бо в запиті воно шукається за точним збігом (false). Далі — інструментальність: ця умова відсіює найбільше зайвого. Мовлення перевіряється останнім.

| Поле зі звіту explain | Без індексу | З індексом |
|---|---|---|
| Як шукали | COLLSCAN | FETCH + IXSCAN |
| Час, мілісекунд | 125 | 37 |
| Записів прочитали | 113 999 | 16 141 |
| Ключів переглянули | 0 | 16 602 |
| Записів повернули | 16 141 | 16 141 |

Читання скоротилося в 7 разів, час — у 3.4 раза. Виграш скромніший, ніж у завданні 1, і це нормально: під умову підходить кожна сьома пісня в базі. Індекс дає найбільше, коли шукаєш голку в копиці сіна, а не цілу жменю.

### Завдання 3 (необов'язкове). Чи є запит «покривним»?

Питання з умови: є індекс `{track_genre, popularity, danceability}` із завдання 1. Чи є покривним такий запит?

```javascript
db.tracks.find({ track_genre: "pop", popularity: { $gte: 70 } });
```

Покривний (covered) — це коли база складає відповідь тільки з покажчика, взагалі не відкриваючи самі записи. Для цього все, що запит повертає, має бути в індексі.

Відповідь: ні, у такому вигляді не є. Причини дві:

1. Запит не вказує, які поля йому потрібні, а значить повертає весь запис: назву, виконавців, характеристики звучання. Нічого цього в індексі немає — доведеться йти по самі записи.
2. Навіть якщо попросити тільки поля з індексу, база за замовчуванням додає ще службове поле `_id`. Його в цьому індексі теж немає. Треба явно сказати `_id: 0` — «не повертай його».

Ми перевірили обидва варіанти через explain:

| Варіант запиту | Стадії | Записів прочитали | Ключів переглянули |
|---|---|---|---|
| Як в умові, без проєкції | FETCH + IXSCAN | 317 | 317 |
| З проєкцією `{_id: 0, track_genre: 1, popularity: 1}` | PROJECTION_COVERED + IXSCAN | 0 | 317 |

Другий варіант — уже покривний: жоден запис не прочитаний (totalDocsExamined = 0), відповідь зібрана з 317 ключів покажчика. Про це прямо каже стадія PROJECTION_COVERED у звіті.

### Бонус. Індекс по списку виконавців

Індекс по полю-списку називається multikey: база записує в покажчик кожне ім'я окремо. Для пошуку `{artists: "Bad Bunny"}` це дало: час з 81 до 2 мілісекунд, прочитаних записів — з 113 999 до 416. Саме цей замір згадується у відповіді на питання 2 частини 1.

### Усі індекси колекції tracks

| Назва | Поля | Для чого |
|---|---|---|
| idx_genre_pop_dance | жанр, популярність (спад.), танцювальність | завдання 1 і покривні запити |
| idx_work_music | explicit, інструментальність, мовлення | музика для роботи |
| idx_artists_multikey | виконавці (список) | пошук за іменем виконавця |

## Про дублікати в датасеті

У базі 113 999 записів, але різних пісень лише 89 740. Так вийшло тому, що автори датасету збирали його по жанрах — приблизно по тисячі пісень на жанр. Пісня, яка належить кільком жанрам, потрапила до вибірки кожного. Наприклад, «Ferrari» (James Hype) лежить чотири рази: у dance, deep-house, groove і house. Разом таких «зайвих» записів 24 259.

Це властивість самих даних, не помилка завантаження. Для жанрових звітів воно не шкодить: у межах жанру пісня зустрічається один раз. Але там, де рахуються пісні виконавця, дублікати прибрано окремим кроком (завдання 2 частини 2), а в завданні 1 наведені обидві цифри — записи й різні пісні. Загальні середні по всій базі трохи зміщені в бік пісень, що належать кільком жанрам одразу, — це варто пам'ятати, читаючи додаткову аналітику.

Якщо колись знадобиться зовсім чиста колекція, дублікати можна згорнути: згрупувати за кодом пісні й зібрати всі її жанри в один список.

## Дрібні примітки

- Замість скріншотів — повні текстові логи в `results/`. Кожен запит надрукований перед відповіддю.
- Паролі й адреса бази (`.env`, `atlas-credentials.env`) та сам датасет (`dataset.csv`) у git не потрапляють — дивіться `.gitignore`.
- Усі скрипти можна перезапускати: вони самі прибирають попередні результати.
